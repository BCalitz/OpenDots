# 4.1 Look back 60 days when you connect

When you connect an account, OpenDots reads the last 60 days so it knows the people you deal with and what is still waiting, without sending two months of mail to Jev or keeping it.

## Today

- A new source looks back 24 hours (`FIRST_LOOKBACK_MS` in `src/server/inbox/account-source.ts`) and each poll returns at most 25 items (`MAX_ITEMS`). There is no paging: Gmail's `search_messages` takes a query and a limit, Outlook's takes a limit only.
- The engine marks the first poll's batch as `initial` (`src/server/inbox/engine.ts`). Push notifications skip an initial batch (`src/server/inbox/notify.ts`). Discovery does not: it judges those items with Jev like any others.
- Memory distills every item, and only asks Jev to match names for items received in the last day (`src/server/memory/service.ts`), so distilling old items is free.
- Items older than the retention window (14 days by default) are pruned once distilled.

## Build

### 1. Paging in the connectors

- Gmail `search_messages`: accept `pageToken` and return `nextPageToken`.
- Outlook `search_messages`: accept `before` and `after` (ISO times) and `pageToken`, and return `nextPageToken`. Today it cannot filter by date at all.
- Teams `list_chat_messages`: accept `before`.
- These are additions. Existing calls keep working.

### 2. A backfill job

A backfill is separate from polling, so new mail keeps arriving while it runs.

```sql
CREATE TABLE backfills(
  source_id TEXT PRIMARY KEY REFERENCES inbox_sources(id) ON DELETE CASCADE,
  owner_id TEXT NOT NULL,
  state TEXT NOT NULL,          -- running, done, failed, cancelled
  days INTEGER NOT NULL,
  judge_days INTEGER NOT NULL,
  cursor TEXT,                  -- the connector's page token
  oldest_at BIGINT,             -- how far back it has reached
  read_count INTEGER NOT NULL DEFAULT 0,
  judged_count INTEGER NOT NULL DEFAULT 0,
  error TEXT,
  started_at BIGINT NOT NULL,
  updated_at BIGINT NOT NULL
);
```

- Connecting an account starts one for each of its mail and message sources. It can also be started from Accounts.
- It reads newest first, one page at a time, and stores its cursor after each page, so a restart resumes where it stopped.
- It waits one second between pages and backs off when the service says to slow down.
- It stops at 60 days back or 5,000 items for a source, whichever comes first. The cap of 2,000 kept items per source does not apply to backfilled items, because step 4 removes them.
- It runs under the same lease and pause rules as polling. Pausing OpenDots pauses it.
- Add `backfill: boolean` to `NewEvents`. Events from a backfill are written with it set.

### 3. What gets judged

**Decision:** Jev only sees a small part of the backfill.

Discovery skips a backfilled item unless one of these is true:

1. It was received in the last `judge_days` (default 7).
2. It is the newest item in its thread, it is not from the owner, and it is not from a sender the rules drop. This is the "someone may still be waiting on you" case.

Rule 2 is worked out in code after the whole backfill has been read, since the newest item of a thread is only known then. Cap it at 100 items per source, newest first.

For mail the owner sent: the newest item of a thread within 30 days, where the owner wrote last, goes through the existing "waiting on others" question. Cap 50.

Before the backfill starts, the screen shows the estimate: "I will read about 60 days of mail. About 180 items will be sent to TypeSafe to be judged. [Start] [Read 7 days only] [Not now]". The count comes from a first cheap pass that lists ids and dates without bodies.

### 4. Distill, then remove

- Every backfilled item is distilled by the memory run with the free tiers only (exact alias, sender and domain, near spelling). No Jev match calls, whatever its date.
- A backfilled item older than the retention window is pruned in the same memory run that distilled it, following the existing rule: only when distilled and nothing still waits on the owner.
- Run memory right after each backfill page, not only every 15 minutes, so old mail is not held longer than needed.

### 5. No interruptions

A backfilled item never causes a push, an investigation that pushes, or a morning-brief entry of its own. What it finds goes to:

- the home screen, in the normal sections;
- one summary in the log when the backfill ends: "I read 60 days of mail. 12 things look like they are still waiting on you, 5 people owe you a reply, and I now know 47 people and companies." Code builds this from counts.

### 6. Progress

`GET /api/backfills` returns each source's state. Accounts shows, per account: "Reading back: reached 3 October, 1,240 items" with **Stop**, then "Read 60 days on 16 November", or the error with **Try again**.

## States

| State                            | What happens                                                              |
| -------------------------------- | ------------------------------------------------------------------------- |
| The service rate-limits          | Waits as told, keeps its cursor, shows "Waiting for Outlook"              |
| The sign-in expires midway       | State `failed`, with **Reconnect**; **Try again** resumes from the cursor |
| The owner stops it               | State `cancelled`; what was read stays                                    |
| TypeSafe is not set up           | Reads and distills; judges nothing; says so                               |
| The mailbox has under 60 days    | Ends at the oldest item                                                   |
| A second backfill for one source | Refused while one is running                                              |

## Not in this spec

The onboarding screens that show this (4.3), calendar history, and backfilling MCP or webhook sources.

## Tests

Use connector fixtures.

- Paging: a three-page mailbox is read fully, newest first, and a restart after page two reads only page three.
- The 60-day and 5,000-item limits each stop it.
- Judging: an item 3 days old is judged; one 30 days old is not; the newest item of an old thread from someone else is; the caps hold; the estimate matches what is then judged.
- No backfilled item causes a push or a brief entry.
- An item 40 days old is distilled and pruned in one memory run; one with an open finding is kept.
- Memory makes no Jev match calls for backfilled items.
- Pause stops the job and resume continues it.
- New mail arriving during a backfill is polled and judged as normal.
