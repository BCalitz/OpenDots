# 1.2 One assistant by default

You talk to one assistant. Spaces, other Dots and the technical views still exist, behind Settings. This spec also sets the limits on what the assistant may do, because the new "What it may do" screen shows them.

Screens: **7 · What it may do** and the top bar on every screen of the [design canvas](https://claude.ai/artifact/C8YuNty1R1zDMZhgmg95VX).

## Today

- The sidebar in `src/client/App.tsx` lists every Dot and Space, plus Activity, Inbox, Accounts, Insights and Memories.
- Discovery hands items to the Dot in `DiscoverySettings.dotId` (`src/shared/inbox-types.ts`).
- Each connection tool has a policy per Dot: allow, ask first or block (`grants`, `grant_policies`). "Always allow" on an approval card saves a rule. Sending mail, payments and deletes can be set to allow after a typed confirmation (`confirm` in `POST /api/chat/approvals/:id`, `src/server/chat-routes.ts`).

## Build

### 1. The assistant

- Add `assistantDotId` to the workspace settings (the JSON in the `settings` table).
- When it is unset, choose it once: the discovery Dot if there is one, else the oldest Dot. On an install with no Dots, create one named "Assistant" with research, memory and connections allowed, and no computer.
- Discovery, the morning brief, the home screen (1.1) and calls (1.3) use this Dot. `DiscoverySettings.dotId` follows it; the separate picker in discovery settings is removed.
- Settings gets a picker to change which Dot is the assistant.

### 2. Navigation

- Replace the sidebar with a top bar: **Today**, **Inbox**, **People**, then on the right the watching status, **What it may do**, **Settings** and **Pause**.
- **People** shows the existing entity list from `GET /api/memory/entities` as a plain list until 5.1 builds the full page.
- Settings holds everything that left the sidebar: Dots, Spaces, Accounts, Activity, Insights, Memories and discovery settings. Each opens the view that exists today, unchanged.
- The watching status lists connected accounts. It turns amber, with the reason, when any account has an error or OpenDots is paused.
- At narrow widths the top bar wraps; nothing is hidden behind a menu that only appears on hover.

### 3. Action groups

**Decision:** in version 1, sending, meeting changes, payments and deletes always ask, every time. They can never be set to "Always allow".

- Give every connector tool a `risk`, set in the connector's own tool definition (`src/server/connectors/gmail.ts`, `microsoft.ts`):

  | Risk      | Tools                                                              | Policy allowed              |
  | --------- | ------------------------------------------------------------------ | --------------------------- |
  | `read`    | Anything that only reads                                           | Runs on its own             |
  | `low`     | File, label, move, mark read; calendar holds and reminders; a task | Ask first, or allow by rule |
  | `send`    | Send or reply to mail and messages                                 | Ask first only              |
  | `meeting` | Accept, decline, move or cancel a meeting with other people        | Ask first only              |
  | `money`   | Anything that pays or commits money                                | Ask first only              |
  | `delete`  | Anything that deletes                                              | Ask first only              |

- For an MCP server's tools, which declare no risk: `readOnlyHint` is `read`; `destructiveHint` is `delete`; everything else is `send`, the strictest non-destructive group, because OpenDots cannot know what it does. The owner can lower one MCP tool to `low` in Accounts, with a warning.
- Enforce in one place, where a policy is written and where "Always allow" is saved: a tool whose risk is not `low` cannot have the policy `allow`. Remove the typed-confirmation path. A migration resets any existing `allow` policy on such a tool to ask first and logs how many it changed.
- Block still works for every tool.

### 4. The "What it may do" screen

A new view, `src/client/PermissionsView.tsx`, with the five groups from the canvas:

1. **Does on its own**: fixed text.
2. **Does without asking, because you allowed it**: every `allow` policy and saved rule, with the account, the date and how often it was used (from `action_log`), and **Remove**.
3. **Asks you first**: `low` tools with no rule.
4. **Always asks you, every time**: the `send`, `meeting`, `money` and `delete` groups.
5. **Never does**: fixed text.

One route, `GET /api/permissions`, returns groups 2 to 4 for the assistant Dot. Removing a rule uses the existing policy route.

The model has no tool that reads or writes this. Nothing a turn does can change a policy.

## States

- **No accounts connected:** groups 2 to 4 are empty; the screen says "Connect an account to see what it can do there" with a link to Accounts.
- **Paused:** a banner at the top of every screen, with **Resume**.

## Tests

- A fresh install creates one assistant Dot; an install with three Dots keeps all three and picks the discovery Dot.
- A `send` tool cannot be saved as `allow` through the policy route or through "Always allow"; the response says why.
- The migration resets an existing `allow` on a `send` tool and leaves a `low` tool alone.
- An MCP tool with no hints is treated as `send`.
- `GET /api/permissions` puts each tool in the right group.
