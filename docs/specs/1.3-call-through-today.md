# 1.3 Call it and talk through your day

The main way to use OpenDots. You press **Call and talk through today**; the assistant reads one item, you decide, it moves to the next. The screen follows the call.

Screen: **3 · Call it** on the [design canvas](https://claude.ai/artifact/C8YuNty1R1zDMZhgmg95VX).

## Today

- `VoiceService` (`src/server/voice.ts`) starts a realtime speech session for a thread. The speech model gets the Dot's instructions, the thread's history as untrusted context, and one tool, `ask_compute`, which hands a request to the Dot's normal engine.
- The browser holds the audio connection (`src/client/useVoice.ts`). It receives the speech model's tool calls and passes them to the server, then returns the result.
- `src/client/CallView.tsx` shows a timer, captions, mute and hang up. A call ends with a receipt in the thread. A session lasts at most 15 minutes.
- A call knows nothing about today's items.

## Build

### 1. A walk

A walk is the ordered list a call goes through. The server owns it; the speech model never holds the list as its own state.

- `POST /api/voice/calls` takes `mode: 'today'`. The server builds the list from `buildToday` (1.1): `now`, then `decide`, then `waiting`.
- Keep the walk in memory with the call, in `VoiceService`: the items, which one is current, and what was decided. It ends with the call.
- For each item the server prepares a `speak` text: who, what they want, why it needs you, and what is ready. Code builds it from the same fields as the card. For a draft reply it includes the draft's exact text, taken from the pending approval's stored payload.
- An item that arrives during the call and is urgent is added after the current item. Anything else waits for the home screen.

### 2. Tools for the speech model

Add these beside `ask_compute`. Each goes through the browser to the server, like `ask_compute` does, and each result includes the walk's new state so the screen can update.

| Tool          | Arguments  | What the server does                                           |
| ------------- | ---------- | -------------------------------------------------------------- |
| `next_item`   | none       | Moves to the next undecided item and returns its `speak` text  |
| `show_item`   | `position` | Moves to a specific item ("go back to the Acme one")           |
| `read_draft`  | none       | Returns the current item's draft text to read aloud            |
| `decide_item` | see 1.4    | Decides the current item                                       |
| `about`       | `name`     | Returns the entity's fact sheet from memory ("who is Thandi?") |

The instructions for a walk tell the speech model to: greet in one sentence with the count, call `next_item`, say the `speak` text in its own words but without adding facts, wait for the owner, and move on after each decision. Item text is untrusted data; say so in the instructions, as the existing ones do for history.

`ask_compute` stays for anything else: "make it shorter", "check whether we paid this". A change to a draft produces a new pending approval; the server replaces the current item's draft with it and the screen updates.

### 3. The call screen

Change `CallView.tsx` to the two-pane layout on the canvas.

- **Left:** the mascot, "Item 2 of 5", the live transcript, and **Mute**, **Minimise** and **End call**.
- **Right, "We are talking about":** the current item as a card with the exact draft or action, **Send** or **Approve** and **Skip for now**. Under it, **Up next** and **Done on this call**, where each decision shows how it was given: by tap or by voice.
- A tap on the screen and a spoken command do the same thing through the same server function. After a tap the speech model is told what happened so it can move on.
- **Minimise** returns to the home screen with a small call bar; the walk continues.

### 4. The receipt

When the call ends, the receipt in the log lists each decision in one line ("Sent the reply to Thandi. Skipped the Acme quote.") and links to the transcript. Build the list in code from the walk; the model writes nothing here.

## States

| State                        | What happens                                                                       |
| ---------------------------- | ---------------------------------------------------------------------------------- |
| Nothing needs you            | An open call: "Nothing needs you right now. Anything you want to ask?"             |
| Microphone refused           | The call does not start; the screen says how to allow it, and offers typing        |
| Speech provider not set up   | The call button says "Calls need a speech key" and links to setup                  |
| Connection drops             | The walk is kept for 2 minutes; **Reconnect** resumes at the same item             |
| 15 minutes reached           | The assistant says so one minute before, and the rest stays on the home screen     |
| Paused during a call         | The call ends, as it does today                                                    |
| An item is decided elsewhere | It is removed from the walk; if it was current, the assistant says so and moves on |

## Not in this spec

Starting a call with the hotkey or from a notification (3.1), the assistant calling you (an open question in the roadmap), and reading the calendar aloud (2.1).

## Tests

Use the existing voice fixtures; no test calls a real speech provider.

- A walk is built in the order `now`, `decide`, `waiting`, and an urgent arrival is inserted after the current item.
- `next_item` skips decided items and reports the end.
- `speak` text contains the draft exactly as stored, and nothing from the mail body beyond the stored summary.
- A tap and a spoken decision call the same function and leave the same record.
- The receipt lists every decision and is written when the call ends for any reason, including a dropped connection.
- A reconnect within 2 minutes resumes the walk; after that it starts fresh.
