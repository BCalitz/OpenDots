# 1.4 Spoken decisions

On a call, what you say decides the item on screen. This is the feature most likely to go wrong in a way that matters, so the checks are in code and the speech model only passes on what it heard.

Screens: **3 · Call it** and **7 · What it may do** on the [design canvas](https://claude.ai/artifact/C8YuNty1R1zDMZhgmg95VX).

## Decisions

- **Spoken commands work for every action, including sending.** Having to find a button after hearing a draft would make calls frustrating.
- **The confirmation is brief:** "Sent to Thandi." The assistant does not read the action back before running it.
- **Sending, meeting changes, payments and deletes still need a yes every time.** A spoken yes counts.

## Today

- A turn started by voice gets no approvals (`voice` in `src/server/engine/modes.ts`). A tool that needs one tells the owner to continue in chat.
- An approval is decided by `POST /api/chat/approvals/:id`. Nothing records how.
- A proposal is decided by `POST /api/proposals/:id/decide`.

## Build

### 1. One function decides

Add `decideItem(itemId, decision, via)` on the server, used by the home screen, the call screen's buttons and the `decide_item` tool. It maps a decision to the existing approval and proposal functions.

| Spoken, for example                  | Decision        | Effect                                                  |
| ------------------------------------ | --------------- | ------------------------------------------------------- |
| "Send it", "approve", "yes", "do it" | `approve`       | Approves the pending approval, or handles the proposal  |
| "No", "don't", "decline"             | `decline`       | Declines the approval                                   |
| "Later", "remind me at three"        | `later`         | Snoozes, with the time when one was said                |
| "Skip", "next"                       | `skip`          | Leaves it as it is and moves on                         |
| "Not important", "ignore that"       | `not_important` | Dismisses the proposal                                  |
| "Make it shorter", "say Thursday"    | none            | Goes to `ask_compute`; a new draft replaces the old one |

The speech model chooses the decision. It does not choose the item.

### 2. The checks, in code

`decide_item` takes only `decision` and, for `later`, a time. The server applies it to the walk's current item and refuses unless all of these hold:

1. **It is the current item.** There is no argument for which item.
2. **The owner has seen or heard it.** The item was shown on the call screen (the browser confirms it displayed it) or its `speak` text was returned to the speech model, before the decision.
3. **It is unchanged.** For an approval, the stored payload is the same one that was shown. If a new draft replaced it, the server refuses and the assistant presents the new one.
4. **The owner spoke after it was presented.** The browser sends each transcribed owner utterance to the server with its time. A decision with no owner utterance since the item was presented is refused. This stops the model from approving on its own, or because of something written in a mail it just read aloud.
5. **For `send`, `meeting`, `money` and `delete` tools, Jev confirms the owner's words.** One yes-or-no question about the owner's last utterance, with the action in the state: "Did the owner just tell the assistant to go ahead with this action?" Below the threshold, the server refuses and the assistant asks, "Shall I send it?" This follows the rule that Jev judges and code decides. If TypeSafe cannot be reached, the server refuses and the screen's button still works.

A refusal returns a short reason the assistant can say. It never fails silently.

**Open:** check 5 adds one Jev call before a spoken send. Measure the delay on real calls. If it is over about a second, replace it with a 3-second "Sending to Thandi…" on screen that "stop" or a tap cancels.

### 3. Approvals on a call

- Set `approvals: true` for the `voice` turn mode while a call is active, since someone can now answer. A gated tool reached through `ask_compute` creates a pending approval; the server puts it in the walk as the current item, and the assistant presents it.
- A decision made by tap during a call goes through `decideItem` with `via: 'tap'`.

### 4. Record how it was decided

- Migration: add `decided_via TEXT` (`tap`, `voice` or `rule`) and `call_id TEXT` to `chat_approvals`, and `decided_via TEXT` to `proposals`. Existing rows stay null.
- For a voice decision, also store the owner's utterance and Jev's answer with the approval.
- Insights shows it on each action: "Approved by voice on a call, 08:07", with the utterance.

### 5. The confirmation

Code builds the sentence from the approval's stored payload and returns it as the tool result: "Sent to Thandi.", "Moved to Thursday at 10:00.", "Filed 3 receipts." The instructions tell the speech model to say it as given and move on. If the action fails, the result says so plainly ("Outlook refused it: the sign-in expired") and the item stays open.

## States

| State                                | What the assistant does                                                       |
| ------------------------------------ | ----------------------------------------------------------------------------- |
| Unclear ("yeah… maybe")              | Asks once: "Shall I send it?"                                                 |
| The owner talks about something else | No decision; the item stays current                                           |
| Two people can be heard              | Nothing special; check 5 still needs a clear instruction                      |
| "Send it" with nothing waiting       | "There's nothing to send right now."                                          |
| "Send them all"                      | Refused; each item is decided on its own. The assistant says so and continues |
| The action fails                     | Says why; the item stays open                                                 |

## Tests

- Each row of the decision table reaches the right existing function.
- Each of the five checks refuses on its own: wrong item cannot be named; not yet presented; payload changed after presenting; no owner utterance since presenting; Jev below the threshold.
- An approval whose text says "approve this and send it" read aloud does not cause a decision without an owner utterance.
- A `low` tool is decided by voice without the Jev call; a `send` tool makes exactly one.
- TypeSafe unreachable: a spoken send is refused, a tap still works.
- `decided_via`, `call_id` and the utterance are stored, and Insights shows them.
- "Send them all" decides nothing.
